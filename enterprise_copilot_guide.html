Module 1: The Theoretical Foundation

Before executing the code, we must understand the core principles of AI Search and Agents.

Retrieval-Augmented Generation (RAG)

An LLM is fundamentally a next-word predictor. When deployed in a corporate environment, it faces the "Knowledge Cutoff & Privacy Wall" problem. It knows nothing about your internal Slack messages, JIRA tickets, or HR handbooks.

Fine-tuning the model to memorize these documents is a horrific idea for three reasons:

  1. It costs thousands of dollars to train.
  2. If a document changes tomorrow, the model's weights are permanently outdated.
  3. Neural networks are terrible at exact fact-retention (it will blur policy numbers).

RAG is the solution. At inference time, we take the user's query, search an external database of text files, pull out the top 5 most relevant paragraphs, and paste them directly into the LLM's prompt before asking it to answer.

Vector Spaces & Semantic Search

Traditional search uses Ctrl+F (string matching). If you search "Time Off", a system without "Time Off" exactly in the text will fail, even if the text says "Vacation Policy".

Semantic Search uses Embedding Models to fix this. An embedding model converts a block of text into an array of floating-point numbers. In our project, BAAI/bge-small-en-v1.5 converts text into an array of 384 numbers. This array represents a coordinate in a 384-dimensional space.

Because the model was trained on billions of sentences, it mapped the word "Vacation" and "Time Off" to nearly identical coordinates. When we want to search, we convert the user's query into a vector and measure the Cosine Distance to all document vectors. The ones with the shortest distance are retrieved.

The BM25 Algorithm (Keyword Search)

Vectors fail catastrophically at highly specific identifiers. If you search for TKT-4912, the vector model might smooth out the numbers and just return "General IT Tickets."

We use BM25 (Best Matching 25) to cover this blind spot. BM25 is an advanced TF-IDF algorithm:

  • Term Frequency (TF): The more times "TKT-4912" appears in a document, the higher the score. It uses an asymptotic curve, so 10 mentions isn't exactly 10x better than 1 mention, preventing keyword stuffing.
  • Inverse Document Frequency (IDF): If a word appears in almost every document (like "the" or "ticket"), its IDF score is basically zero. If "TKT-4912" appears in exactly one document out of 10,000, its IDF score is massive.

Hybrid Search (combining Vector + BM25) is the industry standard for production systems.

Knowledge Graphs & Relational Triples

Search engines return documents. But what if the user's question isn't in a single document? "Who manages the person who owns the Auth-Gateway?"

A Knowledge Graph solves this by storing data as Nodes (Entities like People, Systems) and Edges (Relationships like "MANAGES", "OWNS"). This allows the system to instantly traverse links: (Sarah) -> [MANAGES] -> (Marcus) -> [OWNS] -> (Auth-Gateway), synthesizing an answer instantly.

Agentic Workflows (LangGraph)

A simple RAG app is linear. An Agent is capable of making decisions. It uses a State Machine (via LangGraph) to analyze the query, decide WHICH database to search (Docs vs Tickets), execute the search, evaluate its own answer, and determine if it needs to escalate to a human.

Module 2: The Ingestion Engine (ingest.py)

Before AI can search, we must clean, slice, and structure the data.

Document Extraction (Loaders)

Data exists in wildly different formats. A text file is easy to read, but a PDF contains styling, images, and invisible boundaries. A CSV is a matrix of data. Our loader must handle them all and convert them into standard Document objects with page_content and metadata.

  • TXT: Loaded fully as a single string.
  • PDF: We use PyMuPDF (fitz), which is significantly faster and more accurate than older libraries like PyPDF2. It reads the raw text stream from the binary data page by page.
  • CSV: If we dump a CSV as a single string, the LLM won't understand rows. Instead, we iterate row by row and format it into "Column1: Value | Column2: Value". Every row becomes its own Document.
PII Redaction via spaCy NER

Enterprise data contains Personally Identifiable Information (PII). We cannot store human names or phone numbers in a vector database because doing so creates a permanent privacy violation (you cannot easily 'delete' a name once it is mixed into a vector). We must scrub it BEFORE embedding.

ingest.py - Redaction Logic
def redact(text):
    # 1. Fast Regex for structured PII
    text = EMAIL_RE.sub("[REDACTED_EMAIL]", text)
    text = PHONE_RE.sub("[REDACTED_PHONE]", text)
    
    # 2. Neural Network (NER) for human names
    doc = nlp(text)
    
    # 3. Extract and sort the names by length DESCENDING
    persons = sorted(set(e.text for e in doc.ents if e.label_ == "PERSON"), 
                     key=len, reverse=True)
    
    for p in persons:
        text = text.replace(p, "[REDACTED_PERSON]")
    return text
The "Descending Sort" Data Leak Bug
Why use reverse=True? Imagine the text says: "Dr. Sarah Jenkins". The NER model will extract "Sarah Jenkins" but might also extract just "Sarah". If we replace "Sarah" first, the string becomes: "Dr. [REDACTED_PERSON] Jenkins". We just leaked her last name! By sorting longest to shortest, we ensure the entire name is safely replaced.
The Mathematics of Chunking

Embedding models have a "Context Window" limit. bge-small handles 512 tokens. If we slice the text blindly at 800 characters, we introduce a catastrophic bug.

ingest.py - Sliding Window
def chunk_text(text, size=800, overlap=150):
    chunks, start = [], 0
    while start < len(text):
        end = start + size
        chunks.append(text[start:end])
        
        # CRITICAL: Move back by 'overlap' amount for the next chunk
        start = end - overlap
    return chunks

Why overlap? Imagine the critical sentence is at character 780: "The master password to reset the server is 'Nexa123'." Without overlap, Chunk 1 ends with "The master password to reset the server ", and Chunk 2 begins with "is 'Nexa123'." The context is completely destroyed. Overlapping by 150 characters guarantees that the boundary sentence will appear entirely inside at least one chunk.

Building the Vector and Keyword Databases

Once chunked, the text is pushed to ChromaDB. Chroma automatically batches the API calls to the local huggingface embedding model, generates the 384-dim vectors, and writes them to a SQLite database on disk.

For BM25, we tokenize every document (split by spaces/punctuation) and pass it to the rank_bm25 constructor. We then save the BM25 object using pickle.

Security Warning: Pickling
We use Python's pickle to save the BM25 model to disk. In a production enterprise setting, you should never load pickle files from untrusted sources, as unpickling can execute arbitrary code. For a local system, it's fine, but in prod, we'd use Elasticsearch for keywords.
Graph Construction (NetworkX)

We build a Directed Graph (DiGraph) using NetworkX. Directed means the relationship has an arrow: A -> B is different from B -> A.

  1. Explicit Triples: From the org_chart.csv, we explicitly know the Subject, Predicate, and Object. We add them natively: G.add_edge(Person, Department, relation="WORKS_IN").
  2. Co-mention Inference: Unstructured IT tickets don't have explicit relations. We use spaCy to extract all entities (VPN, ServerX, Marcus) from the ticket. If they appear in the same paragraph, we assume a relationship. We add an edge with relation="CO_MENTIONED" and increment its weight by 1. A weight of 15 means they appeared together 15 times, implying a very strong relationship!

Module 3: The Three-Headed Retriever (retriever.py)

Combining Semantic math, Keyword Math, and Graph Traversal into a single, unified search engine.

Retriever Initialization & Persistence

The Retriever class is a Singleton-like wrapper that holds all three of our databases in RAM (or connected to disk).

retriever.py - Init
class Retriever:
    def __init__(self):
        # Load the SAME embedding model used in ingestion
        emb = HuggingFaceEmbeddings(model_name="BAAI/bge-small-en-v1.5")
        
        # 1. Connect to Chroma DB on disk
        self.chroma = Chroma(persist_directory="data/index/chroma", embedding_function=emb)

        # 2. Unpickle BM25 and the document array
        with open("data/index/bm25.pkl", "rb") as f:
            self.bm25, self.bm25_docs = pickle.load(f)

        # 3. Unpickle the NetworkX Graph
        with open("data/index/graph.pkl", "rb") as f:
            self.graph = pickle.load(f)
Vector Execution & Filtering

When searching ChromaDB, we can inject a filter_dict. This is incredibly powerful. If the LangGraph router decides we only need IT Tickets, we pass filter={"type": "ticket"}. ChromaDB uses its SQLite metadata table to instantly prune the search space before doing the expensive Cosine Math, saving massive amounts of compute time.

BM25 Execution Loop

The rank_bm25 library does not hold metadata. It just returns an array of float scores. We must map these scores back to the original documents using enumerate, sort them, and then manually apply the filter_dict.

Graph Traversal: Successors vs Predecessors

When the query contains an entity (e.g., "Marcus Thompson"), we traverse the graph. Because our Graph is Directed (arrows point one way), we must look in both directions.

retriever.py - Graph Traversal
def search_graph(self, entities):
    results = []
    for entity in entities:
        # Find all exact or partial node matches
        matches = [n for n in self.graph.nodes if entity.lower() in n.lower()]
        
        for node in matches:
            # Outgoing edges: What does Marcus own/do?
            out = [(node, self.graph[node][t].get("relation"), t) 
                   for t in self.graph.successors(node)]
            
            # Incoming edges: Who manages/owns Marcus?
            inc = [(s, self.graph[s][node].get("relation"), node) 
                   for s in self.graph.predecessors(node)]
            
            results.extend(out + inc)
    return results

These Triples (Subject, Predicate, Object) are converted into text strings like "Marcus - OWNS_SYSTEM - AuthGateway" and injected straight into the LLM's prompt.

Rank Fusion: The Math of Consensus (RRF)

We now have two lists of documents: Top 5 from Vector, and Top 5 from BM25. The scores are mathematically incompatible (Distances vs TF-IDF floats). We merge them using Reciprocal Rank Fusion (RRF), which completely ignores raw scores and only looks at their integer Rank (1st, 2nd, etc).

Formula: RRF_Score = 1 / (60 + rank)

retriever.py - RRF Algorithm
def _rrf_fuse(self, sem_results, kw_results, k):
    scored = {}
    
    # 1. Apply formula to Semantic Ranks
    for rank, (doc, dist) in enumerate(sem_results):
        # We use the first 120 chars of the text as a unique ID
        key = doc.page_content[:120]
        scored[key] = {"doc": doc, "rrf": 0}
        scored[key]["rrf"] += 1 / (60 + rank)

    # 2. Add BM25 Ranks to the SAME document score
    for rank, (doc, bm_score) in enumerate(kw_results):
        key = doc.page_content[:120]
        if key not in scored:
            scored[key] = {"doc": doc, "rrf": 0}
        scored[key]["rrf"] += 1 / (60 + rank)

    # 3. Sort by highest RRF score
    fused = sorted(scored.values(), key=lambda x: x["rrf"], reverse=True)[:k]
    return [item["doc"] for item in fused]
A Worked Example
Let's say Document A is Rank #1 in Vector, and Rank #4 in BM25.
Vector = 1 / (60 + 1) = 0.01639
BM25 = 1 / (60 + 4) = 0.01562
Total RRF = 0.03201

Now let's say Document B is Rank #2 in Vector, but didn't even appear in the BM25 list.
Vector = 1 / (60 + 2) = 0.01612
BM25 = 0
Total RRF = 0.01612

Document A destroys Document B! RRF mathematically proves that Consensus is King. A document that both systems agree is "pretty good" will beat a document that only one system thinks is "perfect".

Module 4: The Agentic Brain (agent.py)

Routing, LangGraph State Machines, Prompt Engineering, and Hallucination Guardrails.

LangGraph State vs Chain

A standard RAG pipeline is a linear chain: Prompt -> Retrieve -> Generate. It is rigid and cannot adapt. If the retriever fails to find anything, a chain will just pass empty text to the LLM, causing a hallucination.

LangGraph turns the pipeline into a Directed Graph (a State Machine). Instead of passing parameters between functions, we define a TypedDict called State. The State holds everything happening in the current session. Every node in the graph takes the State, modifies it, and passes it to the next node.

agent.py - State Dictionary
class State(TypedDict):
    question: str          # What the user asked
    route: str             # 'docs', 'tickets', or 'summarize'
    documents: list        # Retrieved doc objects from Chroma/BM25
    graph_context: str     # NetworkX relationships as text
    retrieval_score: float # The RRF math output
    answer: str            # The LLM's final response
    faithfulness: float    # Did the LLM hallucinate? (0.0 to 1.0)
The Deterministic Router

The first node in our graph is the Router. It looks at the user's question and decides which Retrieval Tool to use. Why do we use hardcoded keywords instead of asking the LLM to route it?

Latency and Accuracy. We are running a 3-Billion parameter Llama 3.2 model locally. Small models are notoriously bad at strict classification. Sometimes they return "docs", sometimes "Docs", sometimes "I think it is a document". A keyword router executes in 0.0001 seconds and guarantees 100% deterministic behavior.

Prompt Engineering

Notice how strict the prompt is. We don't just say "answer the question." We enforce specific behavior for edge cases.

agent.py - Prompt
prompt = f"""You are NexaCorp's internal knowledge copilot. Answer using ONLY the context below.
For "who manages/owns/resolves" questions, check the Entity Relationships FIRST.
If the answer isn't in the context, say: "This information is not available in the internal docs. Please raise a ticket on TICKETSYS."
Cite the source.

Question: {q}

Entity Relationships:
{graph if graph else "None"}

Document Context:
{ctx}

Answer:"""
The Faithfulness Metric (Set Theory Math)

We instructed the LLM: "Answer using ONLY the retrieved context." But LLMs are designed to predict the next word—they often sneak in outside knowledge. How do we programmatically detect if the LLM cheated?

We use Token Overlap Set Theory. We break both the Context and the Answer into Sets of words. We then calculate the intersection of those two Sets.

agent.py - Hallucination Guardrail
def compute_faithfulness(answer, contexts):
    # Convert the LLM's answer into a Set of unique words
    answer_tokens = set(answer.lower().split())
    
    # Convert the retrieved documents into a massive Set of words
    ctx_tokens = set()
    for c in contexts:
        ctx_tokens.update(c.lower().split())
    
    # Math: Intersection / Total Answer Tokens
    overlap = answer_tokens & ctx_tokens
    return round(len(overlap) / len(answer_tokens), 2)

If the LLM outputs 10 words, and only 4 of those words actually existed in the retrieved documents, the Faithfulness score is 0.40 (40%). This triggers a massive red warning pill in the UI. If the score is 0.90, we know the LLM pulled the answer directly from the text.

Compiling the LangGraph

Finally, we stitch the nodes together. The router sits at the __start__ node. Based on its output, LangGraph dynamically routes execution to either tool_search_docs, tool_search_tickets, or tool_summarize. Once the tool finishes, all three point to generate to run the LLM, and then to __end__.

Streamlit's Execution Model & Caching

Unlike standard web frameworks (React/Vue), Streamlit is fundamentally synchronous. Every time you type a character or click a button, Streamlit literally runs your Python script from top to bottom again.

Loading the bge-small embedding model, connecting to ChromaDB, and loading the NetworkX graph takes about 5 seconds. If Streamlit did this on every keystroke, the app would be unusable.

app.py - Caching
@st.cache_resource
def get_agent():
    # This heavy initialization only happens ONCE.
    # On subsequent reruns, Streamlit serves the agent from RAM.
    return build_agent()

agent = get_agent()

Module 6: Advanced Architectural Q&A

20 deep, real-world questions testing your understanding of edge cases and design choices.

⭐ Deep Knowledge Database

Q1: Why use BAAI/bge-small-en-v1.5 instead of OpenAI text-embedding-3? ▼
Privacy and Cost. BGE-small is an open-source, 33-million parameter model that runs locally on CPU in milliseconds. OpenAI requires sending sensitive internal company data (like unreleased product specs or HR complaints) to a third-party server, which violates strict Enterprise compliance rules.
Q2: What happens if the query contains no entities for Graph Traversal? ▼
The search_graph function will simply return an empty list []. The string 'None' is injected into the LLM prompt for the graph section, and the LLM relies entirely on the Vector/BM25 results. This is completely safe and handled gracefully.
Q3: Why hardcode the router with keywords instead of using LangChain's LLMRouter? ▼
A 3B parameter model like Llama-3.2 is extremely fast but highly prone to instruction-following failures on complex zero-shot classification. If we ask it to route, it might output 'I think this is a ticket' instead of exactly 'tickets', which crashes the LangGraph conditional edge. Keywords guarantee 100% deterministic routing at 0 latency.
Q4: How does the Faithfulness Metric handle synonyms? ▼
Poorly. Because it uses exact token overlap (Set Theory), if the context says 'vacation' and the LLM generates 'holiday', the overlap score decreases. This is a known limitation of exact-match metrics. However, in strict enterprise environments, a harsh penalty on hallucination is preferred over a loose metric that allows fake facts to slip through.
Q5: Why not use Neo4j instead of NetworkX? ▼
NetworkX stores the graph in RAM and pickles it to disk. This is perfect for 100-1,000 nodes (a hackathon or small org). Neo4j is a persistent, distributed graph database required if your org chart and ticket history spans 1,000,000+ nodes. For this copilot, NetworkX minimizes deployment complexity.
Q6: Can BM25 handle semantic typos? ▼
No. BM25 is a sparse retriever based on exact string matching. If the user searches for 'acess' instead of 'access', BM25 will yield 0 hits. This is precisely why we fuse it with Dense Vector search (which handles typos and semantic meaning beautifully) using RRF.
Q7: What is Reciprocal Rank Fusion actually doing mathematically? ▼
It penalizes models for disagreeing and rewards consensus. The formula `1 / (60 + rank)` gives diminishing returns to the #1 spot vs the #2 spot. If a document is #1 in Vector and #100 in BM25, it might lose to a document that is #5 in Vector and #4 in BM25. It mathematically ensures we only retrieve documents that *both* systems agree are relevant.
Q8: Why is the RRF constant 'k' usually set to 60? ▼
Based on empirical research (Cormack et al., 2009), k=60 prevents the very first rank from mathematically dominating the entire score. If k was 1, rank 1 gets score 0.5, rank 2 gets 0.33, etc. With k=60, rank 1 gets 0.0163, rank 2 gets 0.0161. The curve is smoother, forcing the algorithm to look at consensus rather than absolute peaks.
Q9: Why sort spaCy NER entities by length descending? ▼
To prevent partial string replacement data leaks. If we have entities 'Dr. Sarah Jenkins' and 'Sarah', replacing 'Sarah' first leaves 'Dr. [REDACTED] Jenkins'. Sorting by length descending forces the system to replace the entire 'Sarah Jenkins' block first.
Q10: Why chunk text at all? ▼
Two reasons: 1) Embedding models physically crash if you pass them more than 512 tokens. 2) The 'Lost in the Middle' phenomenon. If you embed a 10-page document into a single vector, the specific details get averaged out. Searching for a specific sentence will fail because the vector represents the 'general vibe' of the whole 10 pages.
Q11: What is the sliding window overlap limit? ▼
We used 800 characters with a 150-character overlap. This guarantees that any sentence shorter than 150 characters will exist completely intact within at least one chunk, preventing context destruction at the chunk boundaries.
Q12: Why use fitz (PyMuPDF) over PyPDF2? ▼
PyPDF2 is outdated, incredibly slow, and struggles with complex multi-column layouts. PyMuPDF is written in C++ and handles OCR, tables, and raw text streams accurately, which is critical for parsing enterprise PDFs without mangling the text.
Q13: How does the UI know which tool was used? ▼
LangGraph's State dictionary contains a tool_used key. When the Router selects a path, the corresponding tool node (e.g., tool_search_tickets) updates the State dictionary with its name. The Streamlit UI simply reads st.session_state.state['tool_used'] to render the badge.
Q14: Is Streamlit secure for production? ▼
Streamlit is excellent for prototyping and internal tools, but it lacks native Enterprise SSO (SAML/OIDC). To deploy this in a real enterprise, you would either put it behind a proxy like Cloudflare Access, or rebuild the frontend in Next.js and expose the LangGraph via FastAPI.
Q15: Why use Ollama? ▼
Ollama acts as a local OpenAI-compatible API server. It automatically handles the heavy lifting of loading GGUF model weights into your GPU (or CPU RAM) and exposes a clean REST API. This abstracts away the horrific complexity of managing PyTorch/Transformers directly.
Q16: What happens if ChromaDB is empty? ▼
The retriever will return an empty list. The LangGraph state will pass this empty context to the LLM. Because of our strict prompt ('If the answer isn't in the context, say...'), the LLM will gracefully tell the user that the internal docs don't contain the answer, avoiding a hallucination.
Q17: Can I add my own JIRA data to this? ▼
Absolutely. You just need to create a new loader in ingest.py that hits the JIRA API, extracts the issue descriptions and comments, structures them as a string, and passes them to chunk_text(). The vector engine will handle the rest.
Q18: Why does Streamlit use @st.cache_resource instead of @st.cache_data? ▼
@st.cache_data is for serializable data (like pandas dataframes). It literally copies the data. @st.cache_resource is for un-serializable objects like Database Connections or AI Models. If you try to cache_data an embedding model, Streamlit will crash with a PicklingError.
Q19: What is the difference between Successors and Predecessors in NetworkX? ▼
In a Directed Graph, A -> B means A manages B. A is the predecessor, B is the successor. If you query 'Who does B manage?', you look at B's successors. If you query 'Who manages B?', you look at B's predecessors. You must check both to get the full relational picture.
Q20: How can we improve the keyword router? ▼
If the keyword router becomes too complex to manage via if/elif, you can upgrade to a fast intent-classification model (like a fine-tuned DistilBERT or SetFit) that runs in 10ms and classifies queries into 'Docs' vs 'Tickets' with 99% accuracy without full LLM overhead.

Module 7: Productionizing to Enterprise Scale

How to take this local prototype to a massive, scalable enterprise architecture.

Scaling the Architecture

This Copilot is a masterpiece of local, privacy-first engineering. However, if the company grows from 100 documents to 10,000,000 documents, the current tech stack will buckle. Here is the upgrade path:

  • From ChromaDB to Qdrant/Milvus: ChromaDB running locally on SQLite is great for under 100k vectors. For millions, you need a distributed vector database like Qdrant or Milvus that runs on a dedicated Kubernetes cluster with High Availability.
  • From rank_bm25 to Elasticsearch: Storing BM25 arrays in a Pickle file is a security risk and uses too much RAM. You must migrate the Keyword Search engine to an Elasticsearch cluster.
  • From NetworkX to Neo4j: NetworkX is an in-memory graph. For a real enterprise, relationships should be persisted in Neo4j, which supports the Cypher query language and scales across multiple nodes.
  • From Streamlit to React+FastAPI: Streamlit's synchronous execution model is terrible for concurrent users. The frontend must be rewritten in React/Next.js, communicating via WebSockets or SSE (Server-Sent Events) to a FastAPI backend that hosts the LangGraph agent.
  • From Ollama to vLLM: Ollama is fantastic for local development. In production, vLLM offers massive throughput improvements (via PagedAttention) for serving Llama models to hundreds of concurrent users on A100 GPUs.
The Core Logic Remains the Same
Even if you replace every single database in this stack, the Agentic Logic, the RRF Math, and the Faithfulness Check remain mathematically identical. You have built the permanent core of an enterprise AI brain.
